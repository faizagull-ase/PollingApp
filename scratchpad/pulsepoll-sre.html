PulsePoll: SignalR Operations Guide

A basic, unauthenticated live-polling application: an operator starts a poll, participants join with a short poll code and submit answers in real time, and the operator closes the poll. This document explains the SignalR mechanics behind that flow and gives SRE the architecture, targets, and runbooks needed to operate it.

Status: Draft Owner: SRE / Platform Auth model: none (poll-code only) Transport: ASP.NET Core SignalR

01 Overview

PulsePoll has exactly four operator/participant actions. Everything in this document exists to keep those four actions fast and available under real-time fan-out load.

Poll start
Operator
Creates a poll, receives a fixed-length join code and question/answer set.
Poll join
Participant
Enters the poll code, joins the poll's real-time group.
Answering
Participant
Selects one predefined option while the poll is open.
Poll closure
Operator
Ends voting; late answers are rejected; results are frozen.
Scope
There is no login, no account, and no participant identity beyond a transient connection. This simplifies the app considerably but shifts several concerns — abuse, rate limiting, poll-code collisions — onto the infrastructure layer. See Section 9.

02 SignalR primer, applied to PulsePoll

SignalR is the real-time layer that pushes poll state to every connected client without polling. The concepts below are the ones that actually shape PulsePoll's reliability characteristics.

Hub

A single PollHub exposes server methods clients invoke (JoinPoll, SubmitAnswer) and pushes client methods the server calls on connections (PollUpdated, PollClosed, AnswerTally). The hub itself is stateless; poll data lives in a separate store so any hub instance can serve any connection.

Groups as poll rooms

Each poll code maps to a SignalR group. Joining a poll calls Groups.AddToGroupAsync(connectionId, pollCode); broadcasting a tally or a close event sends to Clients.Group(pollCode) instead of iterating participants manually. Groups are the mechanism that lets one poll's traffic stay isolated from every other concurrent poll.

Transports and negotiation

A SignalR client negotiates the best available transport in order: WebSockets, then Server-Sent Events, then long polling. Corporate proxies and some mobile networks block WebSockets, so a meaningful share of participants (conference Wi-Fi, locked-down corporate networks) will silently fall back to long polling — higher latency, higher connection count on the load balancer, and more sensitive to idle timeouts. This is a capacity input, not an edge case: assume 5–15% of a large audience will be on a fallback transport.

Connection lifecycle & reconnection

SignalR's automatic reconnect retries the transport on drop but does not replay missed group membership or messages. On reconnect, the client gets a new connectionId, which means the app must explicitly re-join the poll group and re-fetch current poll state (GetPollSnapshot) rather than assuming the group membership survived. Skipping this step is the single most common cause of "participant stopped seeing updates" reports.

Scale-out: the backplane requirement

With more than one hub instance behind a load balancer, group membership and broadcasts must be shared across instances via a backplane (Redis, or Azure SignalR Service acting as a managed backplane). Without it, a broadcast issued on instance A never reaches a participant whose connection landed on instance B, even though both are in the same poll. This is the top scale-out failure mode and is covered in Section 8.

Sticky sessions vs. backplane — pick one deliberately
Either (a) configure the load balancer for sticky sessions so a client's HTTP long-polling requests keep landing on the same instance, and add a backplane for cross-instance group broadcasts, or (b) offload connection management entirely to Azure SignalR Service, which removes the sticky-session requirement from your own load balancer. Running multiple hub instances with neither is the default misconfiguration.

03 Architecture

Minimal viable topology for an unauthenticated, ephemeral polling app: no auth service, no durable per-user data store, poll state held in a fast shared cache with a short TTL.

Component diagram
flowchart LR
    OP["Operator client"] -- HTTPS / WSS --> LB["Load balancer / reverse proxy"]
    PA["Participant clients"] -- HTTPS / WSS --> LB
    LB --> H1["Hub instance A"]
    LB --> H2["Hub instance B"]
    H1 <--> BP[("Backplane\n(Redis / Azure SignalR Service)")]
    H2 <--> BP
    H1 --> STORE[("Poll state store\nkey: poll code, TTL-bound")]
    H2 --> STORE

Why poll state sits outside the hub

Hub instances are treated as disposable: a deploy, an autoscale event, or a crash can take one out at any time without losing poll data, because the poll's question, options, tally, and open/closed state live in the shared store keyed by poll code, not in hub memory. Reconnecting clients re-fetch this snapshot rather than relying on in-memory hub state that may no longer exist on whichever instance they land on next.

Why a poll code, not a poll ID

The fixed-length poll code is both the join key and the SignalR group name. It needs enough entropy to resist casual guessing (see Section 9) but stays short enough for a participant to type on a phone keyboard — typically 5–6 alphanumeric characters, excluding visually ambiguous characters (0/O, 1/I/l).

04 Feature flows

The four features as SignalR method calls and group operations.

4.1 Start poll

sequenceDiagram
    participant O as Operator
    participant API as HTTP API
    participant Store as Poll store
    participant Hub as PollHub

    O->>API: POST /polls (question, options)
    API->>Store: create poll {code, status: Open, tally: 0s}, TTL set
    Store-->>API: pollCode
    API-->>O: pollCode + operatorToken (session-scoped, not auth)
    O->>Hub: connect, JoinGroup(pollCode) as operator

Poll creation is a plain HTTP call, not a hub method — it needs a durable write and a generated code before any real-time connection is useful. The operator's client then opens a SignalR connection and joins the same group participants will use, so it receives live tallies exactly like a participant view.

4.2 Join poll

sequenceDiagram
    participant P as Participant
    participant Hub as PollHub
    participant Store as Poll store

    P->>Hub: connect
    P->>Hub: JoinPoll(pollCode)
    Hub->>Store: lookup(pollCode)
    alt code valid and poll open
        Store-->>Hub: poll snapshot
        Hub->>Hub: Groups.AddToGroupAsync(connId, pollCode)
        Hub-->>P: PollJoined(question, options, currentTally)
    else code invalid or poll closed
        Hub-->>P: JoinRejected(reason)
    end

JoinPoll is the one hub method that needs an explicit rate limit: it is also the endpoint an attacker would use to brute-force poll codes (Section 9).

4.3 Answering

sequenceDiagram
    participant P as Participant
    participant Hub as PollHub
    participant Store as Poll store
    participant Group as Poll group (all clients)

    P->>Hub: SubmitAnswer(pollCode, optionId)
    Hub->>Store: is poll open? has connId already answered?
    alt accepted
        Store->>Store: increment tally[optionId], record connId as answered
        Hub->>Group: AnswerTally(updatedCounts)
        Hub-->>P: AnswerAccepted
    else rejected (closed, duplicate, invalid option)
        Hub-->>P: AnswerRejected(reason)
    end

Duplicate-vote prevention is keyed on connectionId, which is the practical ceiling of what an unauthenticated app can enforce: a participant who reconnects gets a new connection ID and can vote again. If exact one-vote-per-person matters more than simplicity, that requires client-side state (e.g. a stored token) or authentication, both out of scope for this basic version — document this limitation for whoever owns the product decision.

4.4 Poll closure

sequenceDiagram
    participant O as Operator
    participant Hub as PollHub
    participant Store as Poll store
    participant Group as Poll group (all clients)

    O->>Hub: ClosePoll(pollCode)
    Hub->>Store: set status = Closed, freeze tally
    Hub->>Group: PollClosed(finalTally)
    Note over Store: TTL continues counting down;
poll purged after retention window

Closing broadcasts to the whole group so any client mid-submission gets PollClosed instead of a silent timeout. The store keeps the closed poll around briefly (retention window, see Section 10) so late joiners can still see final results before purge.

05 Reliability targets

Suggested starting SLIs/SLOs for a basic live-polling workload. Tune against real traffic once observed.

SLIDefinitionTarget
Connection establishment success Successful SignalR negotiate + connect / total attempts ≥ 99.5%
Join latency Time from JoinPoll call to PollJoined response p95 < 500 ms
Broadcast fan-out latency Time from an accepted answer to tally update received by all group members p95 < 1 s at 1,000 group members
Reconnect recovery Reconnect + re-join group + snapshot refresh, end to end p95 < 3 s
Hub availability Uptime of the SignalR endpoint over rolling 30 days 99.9%
Why fan-out latency is the headline metric
Unlike a typical CRUD API, PulsePoll's user-visible product is the fan-out speed — an operator running a live session in front of an audience will notice a tally lagging by seconds far more than they'd notice an individual API call being slow.

06 Capacity & scaling

Traffic on this kind of app is bursty and correlated: a poll opening or closing generates a synchronized spike from every connected participant at once, not steady background load.

Connection storms

A poll code shared on-screen to a large room produces a join storm within seconds. Size hub instances (or Azure SignalR Service units) for peak concurrent joins per second, not average concurrent connections — the two differ by an order of magnitude in this workload.

Broadcast amplification

Each accepted answer fans out to every group member. Group size, not total connection count, drives per-message cost: a 5,000-person poll broadcasting on every single vote is 5,000 outbound messages per vote. Consider coalescing tally broadcasts (e.g. every 250–500 ms) instead of one broadcast per vote once group sizes exceed a few hundred, trading a small amount of latency for a large reduction in outbound message volume.

Self-hosted hub instance
~5k–10k
concurrent connections per instance, WebSocket-dominant traffic, before CPU/memory tuning is needed — validate against your own hardware.
Azure SignalR Service
1,000 / unit
concurrent connections per Standard unit; scale units horizontally instead of hub instance count.
Fallback transport share
5–15%
of participants expected on SSE/long-polling depending on audience network (corporate, conference Wi-Fi).

Scaling levers, in order of effort

  1. Coalesce/batch tally broadcasts under high group size.
  2. Add backplane capacity (Redis cluster sizing, or additional Azure SignalR Service units) ahead of hub compute — the backplane is usually the first bottleneck, not the hub CPU.
  3. Scale hub instances horizontally behind the load balancer once backplane headroom is confirmed.
  4. Pre-warm capacity ahead of known large scheduled sessions rather than relying on reactive autoscaling, given how fast join storms materialize.

07 Observability

Minimum instrumentation to detect the failure modes in Section 8 before participants report them.

MetricTypeWhy it matters
signalr_connections_activeGauge, per instanceDetects uneven load distribution across hub instances (sticky-session skew).
signalr_connections_negotiated_total by transportCounterTracks WebSocket vs. SSE vs. long-polling mix; a spike in fallback share often precedes a network-related incident.
hub_method_duration_seconds by methodHistogramIsolates whether JoinPoll, SubmitAnswer, or ClosePoll is the slow path.
poll_group_sizeGauge, per pollFeeds the broadcast-coalescing decision and flags abnormally large polls for capacity review.
backplane_publish_latency_secondsHistogramBackplane lag directly becomes fan-out latency; this is the earliest signal of a Redis/Azure SignalR degradation.
join_rejected_total by reasonCounterA spike in invalid_code rejections is the primary signal for poll-code brute forcing.
reconnect_total / reconnect_failed_totalCounterDistinguishes normal network churn from a systemic connectivity issue.

Logging

  • Log connectionId, poll code, and hub instance ID on join/leave/close events for cross-instance tracing.
  • Never log full participant answers alongside any identifying connection metadata beyond what's needed for the duplicate-vote check — keep logs consistent with the no-PII posture in Section 9.
  • Emit a structured event on every ClosePoll with final tally and total participant count, for post-session review independent of the metrics backend's retention window.

Health checks

Expose a liveness check on the hub process itself and a separate readiness check that verifies backplane connectivity (a hub that can accept connections but can't reach the backplane should be taken out of the load balancer pool, not marked healthy).

08 Failure modes & runbooks

Ranked by how directly participants notice them.

Backplane outage or degradation

Critical
  1. Symptom: participants on instance B stop receiving updates broadcast from instance A; single-instance testing looks fine.
  2. Check backplane_publish_latency_seconds and backplane infra health (Redis cluster status / Azure SignalR Service status page) first.
  3. If backplane is down and cannot be restored quickly, fail over to a single hub instance temporarily (accepting a hard connection-count ceiling) so cross-instance broadcast is no longer required.
  4. Once backplane is restored, verify group broadcasts reach all instances before scaling hub instances back up.

Missing sticky sessions on the load balancer

Critical
  1. Symptom: participants on long-polling transport intermittently disconnect or fail to join; WebSocket clients are largely unaffected.
  2. Confirm via signalr_connections_negotiated_total that failures correlate with the SSE/long-polling segment.
  3. Verify load balancer session-affinity configuration (cookie- or IP-based, per your LB) routes a client's successive polling requests to the same instance.
  4. If using Azure SignalR Service, this class of failure shouldn't occur — treat its presence as a signal that traffic is bypassing the service.

Poll-code brute-force / scanning

Warning
  1. Symptom: sustained rise in join_rejected_total{reason="invalid_code"} from a small set of source IPs.
  2. Confirm rate limiting is active on JoinPoll (per-connection and per-IP); if not yet implemented, this is the immediate mitigation.
  3. Temporarily block or throttle offending source IPs at the load balancer/WAF layer.
  4. Escalate to product/security if this recurs — see Section 9 for structural mitigations (code entropy, throttling design).

Thundering herd on a large poll open/close

Warning
  1. Symptom: latency spike on hub_method_duration_seconds correlated with a known large scheduled session starting.
  2. Confirm broadcast coalescing is enabled for the affected poll's group size (Section 6).
  3. If capacity was not pre-warmed ahead of the session, scale hub/backplane capacity manually rather than waiting on autoscaler reaction time.

Client stuck after reconnect (stale poll view)

Minor
  1. Symptom: individual participant reports or stops seeing tally updates after a network blip; other participants unaffected.
  2. Confirm the client re-issues JoinPoll (re-adding to the group) and re-fetches a snapshot on the SignalR onreconnected event, rather than assuming group membership persisted.
  3. If this is systemic rather than one participant, check for a recent client build that regressed the reconnect handler.

09 Security & abuse, given no authentication

"Unauthenticated" is a product decision with specific, enumerable consequences. These are the ones that matter operationally.

Poll code is the only access control
Anyone with the code can join and answer. Treat code length and character set as a security parameter, not just a UX one: a 5-character alphanumeric code (excluding ambiguous characters) gives roughly 28 million combinations — enough to resist casual guessing but not a sustained scripted scan without rate limiting in front of it.

Mitigations to have in place before launch

  • Rate limit JoinPoll per connection and per source IP; this is the primary defense against code enumeration, not code length alone.
  • Rate limit SubmitAnswer per connection to prevent a single scripted client from flooding tallies.
  • Validate all inputs server-side — option IDs must be checked against the poll's actual option set; never trust a client-supplied tally delta.
  • Expire poll codes promptly after closure (see Section 10) so a leaked/guessed old code isn't usable indefinitely.
  • No PII by design: don't collect names, emails, or device identifiers for participants — the absence of authentication is a feature here, not a gap to patch over with informal tracking.
  • TLS everywhere: wss:///https:// only; poll codes and answers otherwise travel in the clear.

Explicitly out of scope for a basic version

Exactly-once voting per human (rather than per connection), operator identity verification, and audit trails tied to a real participant identity all require authentication or persistent client state that this design deliberately omits. Document this as a known limitation rather than an oversight when this guide is handed to stakeholders.

10 Data lifecycle

Everything here is designed to be short-lived, which simplifies both compliance posture and operational recovery.

DataStoreRetention
Poll definition (question, options)Shared cache / store, keyed by poll codeLifetime of poll + short grace period after close
Live tallySame store, in-memory-fastSame as poll definition
Connection → answered-option map (dedup)Same store or hub-local cache backed by the storeSame as poll definition; discarded on purge
Poll codeSame storeReleased back to the available pool after purge, with enough delay to avoid immediate reuse confusion

No participant-identifying data is retained because none is collected. This keeps the data-lifecycle story simple: a TTL on the poll record is sufficient cleanup, with no separate user-data deletion process required.

11 Deployment checklist

  • Load balancer configured for either sticky sessions + backplane, or Azure SignalR Service in front of the hub (not neither).
  • Backplane (Redis or Azure SignalR Service) provisioned with headroom above expected peak join-storm rate, not just steady-state connections.
  • TLS terminated correctly for both the initial negotiate HTTP request and the upgraded WebSocket connection.
  • Idle/keepalive timeouts on the load balancer set longer than SignalR's own keepalive interval, so the LB doesn't drop long-polling connections SignalR still considers alive.
  • Rate limiting deployed in front of JoinPoll and SubmitAnswer (Section 9).
  • Health checks wired to readiness (backplane-aware), not just process liveness.
  • Dashboards built against the metrics in Section 7 before go-live, not after the first incident.
  • Capacity pre-warmed ahead of any known large scheduled session.

12 Glossary

HubThe SignalR server-side class exposing methods clients can call and through which the server can call back into connected clients.
GroupA named set of connections a broadcast can target; used here as the per-poll room.
BackplaneShared infrastructure (Redis, or Azure SignalR Service) that lets multiple hub instances share group membership and broadcasts.
NegotiateThe initial HTTP handshake where a SignalR client and server agree on a transport before upgrading (or falling back).
TransportThe underlying connection mechanism: WebSockets, Server-Sent Events, or long polling, in that fallback order.
Sticky sessionLoad balancer behavior that routes a given client's successive requests to the same backend instance.
